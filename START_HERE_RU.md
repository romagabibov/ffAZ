# AZ/FSHN 1.3.8 — запуск на Vercel

В этой версии паспорт, удостоверение личности, личное фото и поля анкеты шифруются на сервере. Проверку проводит администратор сайта. Оформление AZ/FSHN, публичный каталог, Firebase Auth и текущая база сохранены.

## Если обновляешь работающую 1.3.x

Перенеси содержимое нового архива в корень ffAZ и отправь обычный коммит в main. На Vercel используй Node.js 22.x и обычную Production-сборку с `AFW_PREPARE_FIREBASE` выключенным. Существующая метка готовности Firebase подходит для этой версии. Дальше проверь версию `1.3.8` на `/api/health`, открой `/designers` и **Кабинет → Модель**. Повторно запускать миграцию для обновления с подготовленной 1.3.7 не требуется.

В 1.3.8 исправлены падение вкладки модели и раннее обращение к аккаунту до завершения входа. Плашка профиля соответствует нынешнему округлому оформлению сайта. Новости и образование используют общий публичный кэш; списки могут обновляться с задержкой в несколько минут. Подробности и ограничения проверки находятся в **AUDIT_RU.md**.

- **Handmade** открывается по `/handmade`. Карточки из каталога с категорией ручной работы или украшений показываются там. Кнопка «Написать дизайнеру» появляется после привязки зарегистрированного аккаунта к карточке.
- В **Админка → Показы и события → Создать событие** можно заполнить расписание, дресс-код, правила входа и категории билетов. Время вводится по Баку. Пункты расписания отображаются в порядке добавления. Пустые блоки на странице события скрыты.
- Список в календаре обновляется при открытии страницы и при возврате во вкладку. На сервере и CDN используется короткий общий кэш. Открыв событие, посетитель получает его карточку отдельно. Бронь и покупка сверяют остаток на сервере при каждом действии.
- В админке раздел «Дизайнеры» показывает весь каталог и ищет по бренду и имени дизайнера. Совпадающие записи остаются в базе при нажатии «Добавить недостающие бренды».
- Для проверки пароля открой «Войти / Регистрация» → «Забыли пароль?». Ссылка формируется Firebase Auth. Наличие Email/Password в настройках Firebase Auth и доставка писем зависят от Production.
- В разделе «Статистика» открой «Анкета регистрации» и нажми «Показать ответы». Сводка строится по пяти закрытым вопросам в профилях с отметкой завершения анкеты. 
- Проверь новый путь `/careers?post=true`. В кабинете у каждого вошедшего пользователя видна вкладка вакансий. Владелец может закрыть приём откликов. Существующие отклики остаются в кабинете.
- В админке «Рассылка уведомлений» публикует одно объявление для всех вошедших пользователей. Центр уведомлений увидит его при следующем обновлении. В открытой вкладке проверка идёт раз в две минуты. Действия «прочитать» и «удалить» относятся только к аккаунту пользователя.

## Смена агентства в кабинете

Нажми **Сменить агентство** на плашке кабинета или открой **Редактировать профиль → Представитель агентства**. В списке видны все три встроенных агентства, в том числе текущее: оно подписано и недоступно для повторного выбора. Выбери **Big Model Agency** и отправь запрос. Если карточка встроенного агентства отсутствует в каталоге, она создастся при отправке выбора. Уже занятое другим представителем агентство помечено в списке.

Заявку обычного представителя подтверждает администратор в **Админка → Агентства → Заявки на смену агентства**. Действующий администратор сайта может изменить собственную подтверждённую привязку сразу. После одобрения название на плашке обновляется. Состав моделей связан с карточкой агентства.

Для модели поле **Выбери модельное агентство** находится в редакторе профиля под отметкой **Я модель**. Выбранное название сохраняется в анкете. Официальный статус модели подтверждает представитель агентства. Для нового представителя в редакторе есть выбор агентства и подсказка о подаче заявки.

## Бронирование и покупка

На странице события есть две кнопки. **Забронировать билет** удерживает от 1 до 3 мест на аккаунт для этого события, сразу уменьшает свободный остаток и показывает срок в часовом поясе Баку. Бесплатная бронь заканчивается через 6 часов либо с окончанием мероприятия, если оно наступит раньше. Места возвращаются в продажу по серверному времени. Повторное нажатие открывает текущую бронь с прежним сроком. Брони видны в **Кабинет → Мои билеты → Брони билетов**. Там же раскрываются заявки на розыгрыши, VIP-билеты и купленные билеты.

**Купить билет** открывает отдельную оплату. Для продажи через сайт очисти ссылку организатора и укажи цену и вместимость в карточке события. Если в событии есть ссылка организатора, она открывает его страницу покупки. Остаток на сайте отражает местные брони, а продажу и наличие на внешней странице ведёт организатор. Для события с нулевой ценой выпусти пропуск кнопкой «Получить билет / Get Pass». При покупке через сайт QR появляется после подтверждённой оплаты. Если оплата уже отправлена в банк и результат ещё неясен, места защищены до сверки. При подтверждённой отмене платежа до конца брони исходный срок сохраняется.

## Проходка по QR

Администратору и аккаунтам с ролью `ticket_editor` доступен пункт **Админка → Сканировать на входе**. Для сотрудника с ролью редактора билетов он открывается первым. Выбери мероприятие, нажми **Открыть камеру**, разреши доступ в браузере и наведи телефон на билет гостя. На Vercel используй HTTPS-адрес. При необходимости можно выбрать изображение QR.

Статус **«Вход подтверждён»** означает, что QR обычного или выигранного VIP-билета принят и Firestore сохранил `used`. Повторный скан показывает время первого прохода, если оно сохранено. Чужое мероприятие, отменённый или недействительный билет не дают прохода. Камера распознаёт код на устройстве, а сервер получает код билета и выбранное мероприятие. Для финальной проверки на площадке открой сканер на телефоне волонтёра и пройди один тестовый билет.

## Подключение оплаты ABB ePOS

Эта сборка подготовлена для терминала ABB ePOS на шлюзе Azericard с RSA/SHA-256. Карточные данные вводятся на банковской странице. До получения реквизитов покупки через сайт отключены, а бронь и бесплатные пропуска работают.

1. Уточни в ABB, что договор включает именно профиль Azericard e-commerce. Попроси тестовый и рабочий адреса шлюза, Terminal ID, название мерчанта, открытый ключ шлюза, подтверждённый максимальный срок оплаты и образцы ответов `TRTYPE=90` в JSON для успешного, отклонённого и незавершённого платежа. Включение такого JSON-ответа зависит от настройки терминала. В этой версии рабочий адрес `https://mpi.3dsecure.az/cgi-bin/cgi_link` и тестовый `https://testmpi.3dsecure.az/cgi-bin/cgi_link`. Если по договору другие адреса, подпись или формат ответа, сначала сверим адаптер. [ABB ePOS](https://abb-bank.az/en/biznes/korporativ/online-xidmetler-korporativ/elektron-ticaret) · [Azericard e-commerce](https://developer-test.azericard.com/)
2. Создай пару RSA 2048 по инструкции Azericard и передай банку открытый ключ мерчанта. Приватный ключ мерчанта храни в секретах Vercel. Для возврата с банковской страницы укажи свой HTTPS-домен и путь `/api/payments/abb/callback`. Например, `https://ff-az.vercel.app/api/payments/abb/callback`. Сервер проверяет подпись и сам запрашивает статус платежа у шлюза.
3. Попроси выдать тестовый терминал для прогона с Firebase Emulator. Для возврата из банка потребуется тестовый HTTPS-адрес сервера, через который открывается сайт с эмуляторами. Проверь успешную и отклонённую оплату, закрытие страницы до и после отправки платежа, срок кассы, повторный callback и наличие отдельных QR у заказа из трёх мест. Найденное расхождение с форматом ответа банка нужно исправить перед подключением Production. Платёжные проверки в архиве используют имитацию банка.
4. Когда тестовый терминал пройден, внеси рабочие данные в **Vercel → Project → Settings → Environment Variables → Production** и сделай Redeploy. Оставь действующий `CRON_SECRET`. Значение `paymentsConfigured: true` на `/api/health` показывает, что конфигурация загружена. Приём подтверждает контрольная операция с банком.

| Переменная | Что записать |
| --- | --- |
| `APP_URL` | HTTPS-адрес сайта без пути |
| `ABB_EPOS_GATEWAY_URL` | Подтверждённый URL шлюза |
| `ABB_EPOS_TERMINAL` | Восьмизначный Terminal ID |
| `ABB_EPOS_MERCHANT_NAME` | Название мерчанта для страницы банка |
| `ABB_EPOS_MERCHANT_PRIVATE_KEY` | PEM приватного ключа мерчанта |
| `ABB_EPOS_GATEWAY_PUBLIC_KEY` | PEM открытого ключа банка |
| `ABB_EPOS_CHECKOUT_TTL_SECONDS` | Максимальный срок, в котором банк принимает и завершает платёж, от 1 до 3600 секунд |

Срок оплаты берётся из подтверждённого профиля терминала. Если срок на банковской стороне гарантирован только для начала операции, а после него платёж ещё может завершаться, перед запуском нужно отдельно согласовать сверку просроченных платежей. Документация Azericard указывает окно запроса статуса в 24 часа. При неопределённом ответе банка сервер оставляет покупку на сверке и сохраняет места. Ежедневный cron служит дополнительной проверкой, основной путь — callback и кнопка «Проверить оплату». Порядок ручной сверки таких операций согласуй с ABB при тестировании.

При годовой оплате Pro стоит **275 AZN**, Elite VIP стоит **539 AZN**. Это 12 месяцев доступа за стоимость 11. Разовый слот вакансии стоит **7 AZN**. Слот зачисляется после оплаты, затем пользователю доступна публикация на 30 дней. Автопродление в этих платежах отсутствует.

## Срок хранения событий и билетов

Календарь скрывает завершённые события по дате окончания. Если указали только начало, за окончание берётся конец дня в Баку. Задание `/api/internal/site-maintenance` обрабатывает записи ежедневно небольшими пакетами. Оно учитывает неопределённые платежи, очищает завершённые события и сохраняет билеты шесть календарных месяцев. На билете после окончания видно время до удаления. Для старых билетов дата восстанавливается из сохранившихся данных события или билета. Если даты нет в обоих местах, запись сохраняется для ручной сверки.

## Перед первым деплоем

1. Распакуй архив в отдельную папку. Перенеси файлы в корень репозитория ffAZ. Рядом должны лежать `package.json`, `package-lock.json`, `vercel.json`, `src` и `api`. Архивы предыдущих версий из `public` убери. Проекту нужен **Node.js 22.x**.
2. Проверь настройки Vercel. Framework — Vite, Install Command — `npm ci`, Build Command — `npm run build:vercel`, Output Directory — `dist`. Включи предоставление системных переменных Vercel, в том числе `VERCEL_ENV`. Код определяет рабочую среду по `VERCEL_ENV=production`. Проверь, что домен приложения внесён в Firebase Authentication → Settings → Authorized domains.
3. Сохрани рабочие `FIREBASE_SERVICE_ACCOUNT_JSON`, `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` и `CLOUDINARY_API_SECRET` в **Production Environment Variables**. Все три значения Cloudinary должны относиться к одному окружению. Для собственного домена укажи `APP_URL` в формате `https://example.com` без конечного слеша.
4. Добавь две отдельные секретные переменные Production. Для `AFW_IDENTITY_KEY` используй 32 случайных байта в Base64. Для `CRON_SECRET` используй другое случайное значение длиной от 32 символов. Запусти эту команду дважды и сохрани два разных результата в менеджере секретов. В Git и браузерный код эти значения не должны попадать.

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

## Обновление рабочей базы

Проект Firebase — `gen-lang-client-0062214114`. База Firestore — `ai-studio-azerbaijanfashio-b10348c6-25cd-492e-be41-1af4b42fea93`. Эти значения взяты из конфигурации предыдущей версии. Сверь оба идентификатора в консоли перед обновлением. Сервисный аккаунт для подготовки должен иметь права на данные Firestore, чтение Firebase Auth, управление правилами и индексами.

- Если в Firestore уже есть `users/{UID}` с `role: "superadmin"`, отдельная настройка роли обычно не требуется. Проверь, что это действующий администратор. Если в базе ещё нет такой записи, укажи `AFW_INITIAL_SUPERADMIN_UID` в Production. UID берётся в Firebase Authentication → Users у своего активного аккаунта с подтверждённой почтой. Подготовка один раз назначит роль этому аккаунту. Ранее зашитые в код адреса почты больше не дают административных прав.
- Включи `AFW_PREPARE_FIREBASE=1` в Production и запусти Deploy. Для базы после 1.2.x первый запуск отключает готовность старого API и выводит время следующего запуска в UTC. Сделай Redeploy после указанного времени, примерно через 11 минут. Этот интервал нужен для истечения кэша готовности старой версии и завершения её запросов. Старый интерфейс может оставаться доступным, а рабочие API и отправка форм временно приостановятся. Для чистой базы с настроенным суперадминистратором подготовка идёт в одном запуске.
- Подготовка применяет правила и индексы, переписывает старые анкеты, удаляет дубли в миграционных копиях анкет и очищает публичные карточки от найденных дублированных данных. При большой базе процесс сохраняет курсоры и может потребовать несколько запусков. Лимит по умолчанию — оценочные 8 000 чтений документов за запуск. Допустимый диапазон `AFW_PREPARE_READ_BUDGET` — 200–20 000. Индексы и возможные повторы транзакций могут добавлять расход. Если дневная квота исчерпана, продолжи после сброса квоты.
- После успешной подготовки убери `AFW_PREPARE_FIREBASE` и, если добавлял, `AFW_INITIAL_SUPERADMIN_UID`. Постоянно храни `AFW_IDENTITY_KEY` и `CRON_SECRET` в Production. В обычных сборках Vite не выполняет миграцию. При смене ключа сохрани действовавший ключ в `AFW_IDENTITY_PREVIOUS_KEYS` до истечения срока хранения всех записанных им объектов. Несколько прошлых ключей разделяются запятыми.
- Для запуска подготовки со своего компьютера установи зависимости и задай те же серверные переменные через защищённый локальный `.env` или окружение процесса. Команда `--plan` только показывает идентификаторы проекта и базы. Команда `--apply` меняет выбранную базу.

```powershell
npm ci
npm run firebase:prepare -- --plan
npm run firebase:prepare -- --apply
```

## Проверка перед приёмом документов

1. Открой `/api/health` на рабочем домене. Ожидаемые поля — `version: "1.3.7"`, `ok: true`, `firebasePrepared: true`, `identityEncryptionConfigured: true`, `identityRetentionConfigured: true`, `cloudinaryConfigured: true`. Этот ответ подтверждает наличие настроек и готовность базы. Возможность чтения и удаления в аккаунте Cloudinary проверяется отдельно.
2. Войди под обычным аккаунтом и отправь заявку с двумя **вымышленными** изображениями JPG, PNG или WebP. Открой её в кабинете и под администратором, затем проверь отказ в доступе под другим пользователем и гостем. Одобри тестовую заявку и проверь, что в кабинете появился статус. Убедись в работе входа, кабинета, каталога и сообщений.
3. Проверь Cron Jobs в Vercel и результат первого ежедневного запуска `/api/internal/identity-retention`. Журнал содержит числа удалений и ошибок. Защищённый маршрут использует `CRON_SECRET`, настроенный Vercel, для запуска.
4. Посмотри итог миграции. Если старый объект отсутствует, слишком велик или его исходный URL не связан с записью владельца, защищённая версия подавляет ссылку и предлагает повторную загрузку для незавершённой заявки. Исторические публичные копии за пределами управляемых объектов и ранее созданные резервные копии требуют проверки в исходном хранилище. Ограничь доступ к URL старых деплоев, особенно версий, выпущенных до защиты документов.

## Диагностика

| Сообщение | Что проверить |
| --- | --- |
| `server_configuration_required` | Firebase service-account JSON, проект и корректность Base64-ключа в Production. |
| `firebase_setup_required` | Выполни подготовку через флаг Vercel или команду `--apply`. |
| `identity_setup_required` | Задай `AFW_IDENTITY_KEY`, `CRON_SECRET` и все три значения Cloudinary, затем сделай Redeploy. |
| `No superadmin in Firestore` | При первом развёртывании добавь свой `AFW_INITIAL_SUPERADMIN_UID` или проверь наличие роли в базе. |
| `V2 API was stopped for identity migration` | Повтори подготовку после UTC-времени из лога. |
| `PERMISSION_DENIED` | Права сервисного аккаунта, целевые проект, база и окружение Cloudinary. |
| `FAILED_PRECONDITION` или `missing index` | Статус создания индексов Firestore. Применение индексов может занимать несколько минут. |
| `RESOURCE_EXHAUSTED` | Дневная квота выбранной базы. Миграция продолжится с контрольной страницы. |
| `mode: demo` | Открыт Preview либо локальная сборка. Используй Production для работы с реальной базой. |

## Локальный запуск

`npm run dev` и Vercel Preview используют встроенные данные. Для полноценной локальной проверки нужны Node.js 22 и Java 21+. Команды проверки проекта — `npm run typecheck`, `npm test`, `npm run test:emulator`, `npm run build`. Для тестового входа запусти `npm run emulators` и `npm run dev:emulator` в двух терминалах. Эмуляторы работают с проектами `demo-afw-local` и `demo-afw-secure`. Сценарий проверки файлов в автоматических тестах подменяет Cloudinary. Для штатной загрузки проверочной картинки нужен настроенный Production.
