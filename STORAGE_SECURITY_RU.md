# Хранение документов и расход Firestore

## Как работает текущая схема

Vercel принимает заявку по HTTPS, проверяет токен Firebase и роль. Зашифрованные поля хранятся в Firestore, оригинальные байты фото шифруются до отправки в приватный `raw/authenticated` объект Cloudinary. Ключ выдаётся только серверной среде. По запросу владелец заявки или администратор получают исходное изображение через API. Ссылки Cloudinary с подписью остаются на сервере. Публичный фронтенд получает только обычные материалы. [Справочник Cloudinary Upload API](https://cloudinary.com/documentation/image_upload_api_reference)

Пример срока при решении 14 ноября. Фото становятся недоступны 14 февраля, поля анкеты 14 августа. Точные сроки считаются календарными месяцами в UTC. Заявка на рассмотрении хранится до решения. Черновые фото, которые пользователь загрузил и не прикрепил к заявке, становятся недоступны через 24 часа. Если заявитель повторно подаёт отклонённую анкету на том же пути, текущая копия анкеты заменяется, а старая фотография сохраняет уже заданный срок удаления, когда он был назначен. Логин в Firebase Auth и обычный профиль живут по правилам аккаунта.

Контроль срока работает при выдаче данных. Физическое удаление происходит ближайшим успешным ежедневным проходом отдельными пакетами. Расписание `25 3 * * *` соответствует 07:25 в Баку. На Vercel Hobby запуск может происходить в любой момент этого часа. При ошибке Cloudinary задание попробует убрать элемент в следующий запуск. После истечения срока ни ошибка задания, ни очередь не продлевают выдачу файла через сайт. Ограничения одного прохода — 32 файла и 80 анкет. При потоке стабильно выше 16 решений в сутки с двумя фото или при росте черновиков проверь остаток просроченных файлов и масштабируй частоту или обработчик. [Документация Vercel Cron](https://vercel.com/docs/schedules/cron-jobs/manage-cron-jobs)

Для новых фото указан `backup: false`, для удаляемых объектов включена очистка CDN. Cloudinary может сохранить объект в ранее настроенной резервной копии. Прежние бэкапы Firestore, файлы вне подключённого хранилища и уже скачанные экземпляры контролируются отдельно. Настройка источников старых копий нужна, если срок удаления должен охватывать и эти экземпляры. [Cloudinary об удалении и бэкапах](https://cloudinary.com/documentation/image_upload_api_reference#destroy_method)

## Сколько операций расходуется

| Сценарий | Оценка по коду 1.3.0 |
| --- | --- |
| Первая полная страница кратких анкет | 50 прочитанных документов анкет + 3 документа проверки роли. |
| Открытие одной анкеты администратором | 1 запись статуса + 1 зашифрованная анкета + 3 чтения контекста роли. |
| Просмотр одного фото администратором | 1 запись файла + 3 чтения контекста роли. Для фото владельца только 1 запись файла. |
| Две загруженные фотографии | 4 записи метаданных фотографий и отдельные операции счётчика загрузок. Содержимое уходит в Cloudinary. |
| Пустое ежедневное удаление | Два запроса Firestore с минимальным списанием по одному чтению на запрос, плюс проверка готовности при холодном запуске. |
| Разовая миграция | До 8 000 оценочных чтений документов за проход по умолчанию. Доступен повтор с сохранённой позиции. |

В таблице показаны операции конкретных API. Другие части вкладки, вход, выдача каталога, курсоры, повторы транзакций, индексы и проверка готовности учитываются отдельно. Размеры пакетов и кэша публичной ленты сохранены из 1.2.1. Суммарный дневной расход зависит от данных и визитов. Проверяй его в Firestore Usage по нужной базе. Для выбранной бесплатной Standard-базы документация указывает 50 000 чтений и 20 000 записей в сутки, бесплатная квота может применяться только к одной базе проекта. По архиву нельзя определить тариф и наличие квоты именно у работающей базы. [Биллинг Firestore](https://firebase.google.com/docs/firestore/pricing) · [Квоты](https://firebase.google.com/docs/firestore/quotas)

### Календарь и кабинет модели в 1.3.6

| Действие | Расход до обновления | Расход после обновления |
| --- | --- | --- |
| Открыть календарь | Подписка на выборку до 100 документов Firestore для каждого посетителя | До 100 документов на заполнение общего кэша. При попадании в кэш чтений документов событий нет. |
| Отобразить счётчик объявлений агентства в кабинете | Загрузка до 100 документов с объявлениями | Один ограниченный запрос `count()`. Firestore тарифицирует агрегирование по индексным записям и учитывает минимум одно чтение документа на запрос. |
| Открыть вкладку модели | Сразу подключаются выборки объявлений и уведомлений | Объявления и уведомления читаются, когда открыта соответствующая вкладка. Выборка уведомлений ограничена 50 документами. |
| Перейти из «Дизайнеров» в Handmade | Обе категории были частью одного каталога | Оба адреса используют ту же выборку и тот же кэш каталога. |

Пример для календаря. При 30 документах в выборке и 20 открытиях с попаданием в один общий кэш получается около 30 чтений документов событий вместо 600 первоначальных чтений. Заполнения разных экземпляров кэша, минимальные списания и дополнительные чтения учитываются отдельно. Дневной расход рабочего проекта определяется по Firestore Usage. [Тарификация Firestore](https://firebase.google.com/docs/firestore/pricing)

## Что выбрать дальше

| Вариант | Когда подходит | Что придётся обслуживать |
| --- | --- | --- |
| **Текущий Firestore + приватный Cloudinary** | Ручная проверка на старте и небольшой поток. Фотографии хранятся отдельно от БД. | Доступ администраторов, ключ приложения, ежедневное удаление, политика бэкапов и тариф Cloudinary. |
| **Отдельный приватный объектный бакет** | Когда нужно отделить паспорта от публичных медиа и дать документам собственные IAM, регион и политику хранения. | Private Blob или отдельный бакет R2/GCS, проверка доступа на сервере, учёт операций и сроков удаления. Для GCS учти soft delete и поведение версий. Cloud Storage for Firebase требует Blaze. [Private Blob](https://vercel.com/docs/vercel-blob/private-storage) · [Тариф R2](https://developers.cloudflare.com/r2/pricing/) · [GCS soft delete](https://docs.cloud.google.com/storage/docs/soft-delete) · [Firebase Storage](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024) |
| **Свой сервер или гибрид** | Когда есть конкретное требование к месту хранения и человек, который обслуживает инфраструктуру. Фронтенд может остаться на Vercel, отдельный сервис принимает и хранит шифрованные документы. | Сетевой доступ, обновления, резервирование, проверка восстановления, аудит доступа, ключи и гарантии удаления. У Vercel Functions доступна временная файловая область `/tmp`. [Файловая система Vercel](https://vercel.com/docs/functions/runtimes#file-system-support) |

Для масштаба. Сто решений в месяц при двух фотографиях по 1 МБ на заявку и трёх месяцах хранения дают около 600 МБ активных фото при равномерной нагрузке. Сюда добавляются ожидающие заявки и черновики. Переезд фото в другой бакет сам по себе экономит хранилище медиа. Главные расходы Firestore по-прежнему дают объёмы выборок и подписок. Для небольшого потока есть смысл оставить текущую схему. Если понадобится сильнее отделить доступ к документам, следующий шаг — отдельное закрытое хранилище с отдельными ключами и политикой резервирования.
